# Metrics for Tracelet Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Quickmeet exports a small set of metrics (request latency, calls and participants right now, call length, join-token outcomes, push deliveries, rate-limit rejections) to Tracelet over OTLP/HTTP, which needs metrics support in the `otel` package of `letgo-packages` first.

**Tech Stack:** let-go 1.13.0, lgx 0.4.2, Go OpenTelemetry SDK v1.47.0 (`sdk/metric`, `otlpmetrichttp`), the `otel` package in `~/Projects/letgo-packages/otel`, Tracelet as the receiver.

## Design

### Why two repos in one plan

Tracelet ingests metrics (gauges, sums, explicit-bucket histograms; cumulative or delta). The `otel` package pinned by quickmeet (`otel-v0.1.0`) has traces and logs only, so nothing can be emitted until the package grows metrics. The work is therefore two parts with a release between them:

1. **letgo-packages `otel`** (a branch and PR in `~/Projects/letgo-packages`): add a metrics provider and three instrument calls to the Go shim and the let-go veneer, release as `otel-v0.2.0`.
2. **quickmeet**: bump the pin, add the metric helpers to `quickmeet.telemetry`, a small catalog namespace `quickmeet.metrics`, and instrument seven metrics.

While quickmeet is developed, `lgx.edn` points at the local checkout (`{:local/root "../letgo-packages/otel"}`) so both sides can be exercised before the tag exists. The last quickmeet task switches it to the tag.

### The `otel` additions

The package keeps its shape: one opaque `*Handle`, plain maps for options, no dynamic vars. Three functions, instruments created lazily by name and cached on the handle (a `sync.Map` keyed by kind and name):

| Function | Instrument | Value |
|---|---|---|
| `(counter-add! h name n attrs)` / `(counter-add! h name n attrs opts)` | Int64 counter (monotonic sum) | integer |
| `(record! h name v attrs)` / `(record! h name v attrs opts)` | Float64 histogram, explicit buckets | number |
| `(gauge-set! h name v attrs)` / `(gauge-set! h name v attrs opts)` | Float64 **synchronous** gauge (`Meter.Float64Gauge`) | number |

- `opts` are `:unit`, `:description`, and for a histogram `:buckets` (a vector of boundaries, ascending). They apply only when the name is first used; later calls' opts are ignored (documented).
- `attrs` follow the span rule: string/keyword keys, string/int/float/boolean values, anything else dropped, never thrown on.
- A no-op handle (no endpoint) has no meter provider; all three return nil immediately.
- **Gauges are pushed, not observed.** An observable gauge would make the SDK call a let-go function from its own goroutine at export time. Whether the let-go VM tolerates that is unverified, and the shared-binding-stack issue (`docs/backlog/letgo-http-handlers-share-dynamic-bindings.md`) says to assume it does not. A synchronous gauge keeps the SDK side pure Go and lets quickmeet set the value at the moment it changes.
- Exporter: `otlpmetrichttp`, wrapped in the SDK's `PeriodicReader`. Default aggregation (explicit-bucket histograms; Tracelet rejects exponential ones), default cumulative temporality. The reader's interval is the SDK's default (60 s), overridable with `OTEL_METRIC_EXPORT_INTERVAL`; `Shutdown` does a final collect and flush, so the last interval is not lost.
- Configuration follows the existing per-signal rule: `:endpoint` and `:headers` are passed to the metric exporter only when `OTEL_EXPORTER_OTLP_ENDPOINT` / `_METRICS_ENDPOINT` and `OTEL_EXPORTER_OTLP_HEADERS` / `_METRICS_HEADERS` are unset. `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` joins the "is it configured" check in `Start`.
- An instrument the SDK refuses (invalid name) is printed once to stderr and replaced by a cached no-op, so a bad name never throws into a request.

### The quickmeet metrics

Names and units follow the OpenTelemetry HTTP conventions where one exists, so Tracelet's per-route percentile queries work as written. Attributes are **only bounded values**: route patterns, outcomes, bucket names. Never a room id, user id, email, or raw path (same rule as span names, and worse here: each distinct value is a series).

| Metric | Type, unit | Attributes | Recorded where |
|---|---|---|---|
| `http.server.request.duration` | histogram, `s`, buckets 0.005 … 10 | `http.request.method`, `http.route` (the pattern), `http.response.status_code` | `telemetry/wrap-route`, in a `finally`; an exception counts as 500 |
| `quickmeet.calls.active` | gauge | none | `history/record!` after each webhook event; at startup |
| `quickmeet.participants.active` | gauge | none | same |
| `quickmeet.call.duration` | histogram, `s`, buckets 30 s … 4 h | none | `history` `finished!` (a `room_finished` event) only |
| `quickmeet.token.requests` | counter | `outcome`: `ok`, `full`, `not_found` | the token route |
| `quickmeet.push.deliveries` | counter | `outcome`: `sent`, `gone`, `failed` | `push/deliver-one!` |
| `quickmeet.rate_limit.rejected` | counter | `bucket`: `signin`, `signup`, `create_room`, `ring` | `routes/limited` |

Decisions:

- **Gauges come from webhooks plus SQLite.** Every join, leave and room end reaches the app as a webhook, so after `history/record!` applies an event it counts open calls and present participants (two cheap queries) and sets both gauges. At startup the handler's init sets them (after `close-open-calls!`, so they read 0). This needs no SFU round-trip and no callback from the SDK. The cost: a lost webhook leaves a gauge stale until the next event. Acceptable on one box; the same weakness the call history already has.
- **Call duration only from `room_finished`.** Calls closed at startup/shutdown or because a stale one was found at the next join have an end time that is overstated (see `db.lg`, `close-open-calls!`); they would pollute the histogram. Duration is the seconds from the call's earliest participant `joined_at` to the event's `createdAt`.
- **`quickmeet.metrics` is a catalog, not a framework.** One small namespace with one function per metric (`calls-active!`, `token-request!`, …; the request duration lives beside `wrap-route`, see Task 7) holding the name, unit, buckets and attribute keys, so call sites are one line and the list of metrics lives in one file. It calls three generic helpers in `quickmeet.telemetry` (`count!`, `record!`, `set-gauge!`) which, like `log!` and `in-span`, read the process-wide handle atom and fall through to nothing when telemetry is off.
- **Request duration uses `System/currentTimeMillis`** (the clock the rate limiter already uses), divided by 1000.0. Millisecond resolution is plenty against a 5 ms first bucket.
- **Not included (YAGNI, a line each later):** signups and rooms created, SFU lookup failure counter (already a log line and an errored child span), per-room anything.

### Testing

- **otel package:** the fake OTLP receiver already in `core_test.lg` records request paths; extend it to record the raw body as a string (protobuf strings are literal, so a test can look for a metric name without decoding, as `docs/KNOWLEDGE.md` notes for span names). Tests: metrics reach `/v1/metrics` on shutdown with the metric names in the body; the per-signal env override moves only the metric endpoint; a no-op handle accepts all three calls; a bad name does not throw.
- **quickmeet:** pure functions are tested directly (new `db` count and duration queries). The helpers and the catalog are tested against a stub receiver like `telemetry_test.lg` does. A route test proves `http.route` carries the pattern and the raw room id never appears in the export. Existing tests must pass unchanged, which is the proof that telemetry-off falls through.
- **End to end:** run a real Tracelet locally, start quickmeet against it with `OTEL_METRIC_EXPORT_INTERVAL=5000`, make a few requests, and read the metrics back with `tracelet metrics list` / `query`. This is the check the fake receiver cannot give (values, attributes, units).

## Summary (2026-10-13)

**Implemented.** `letgo-packages` `otel` gained `counter-add!`, `record!` and `gauge-set!` (PR #6, tag `otel-v0.2.0`). Quickmeet exports seven metrics: `http.server.request.duration`, `quickmeet.calls.active`, `quickmeet.participants.active`, `quickmeet.call.duration`, `quickmeet.token.requests`, `quickmeet.push.deliveries` and `quickmeet.rate_limit.rejected`, through `quickmeet.telemetry` helpers and the `quickmeet.metrics` catalog. Docs: `docs/CONFIGURATION.md`, `docs/KNOWLEDGE.md`. Full suite on the pinned tag: 111 tests, 0 failures (`participants-of-an-unknown-room` is a known flake, `docs/backlog/system-test-sfu-unreachable-at-start.md`, and did fail once in a full run).

**Deviations** are the `> Deviation:` notes above: hand-edited `go.mod`, whole-number counters, the settle loop for concurrent gauge writes, `gone` counted after the delete, a zero clamp instead of a monotonic clock. No session task list was kept: `TaskCreate` was not available in this environment, so this document is the only record.

**Not checked live:** `quickmeet.push.deliveries` against a real device (stub push service only). A stray `otel: failed to upload metrics: ... context canceled` line can appear on stderr when a very short `OTEL_METRIC_EXPORT_INTERVAL` collides with shutdown; it did not appear with the default interval.

**What the plan could have specified better:** that shutdown sends a metrics request even with nothing recorded (it broke four existing assertions), that gauge writes from concurrent webhooks need a repair step, and that let-go has neither `locking` nor a monotonic clock.
