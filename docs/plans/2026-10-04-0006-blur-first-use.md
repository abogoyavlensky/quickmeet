# Blur's First Use Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The first blur on a new device takes a fraction of the time it takes today, and while it loads the button says so.

**Tech Stack:** Caddy's `encode` directive in the three Caddyfiles (`compose.yaml` x-caddy, `deploy/Caddyfile`, `deploy/docker/Caddyfile`); plain JavaScript and CSS in `resources/public/room.html` and `resources/public/app.css`; Playwright e2e (`lgx e2e`); Docker for the local Caddy check.

---

## Design

### The problem

The first blur on a device fetches MediaPipe's wasm, 9.4 MB, plus its
loader and the model (`/static/blur/<tag>/...`, cached for a year after
that, see the 2026-10-01 blur plan). Nothing compresses it: the app
serves raw bytes and none of the Caddyfiles enables compression, so Caddy
passes the 9.4 MB through as is. On top of the download the browser
compiles the wasm and MediaPipe warms up WebGL, a second or two on a
laptop and several on a phone; browsers cache the compiled wasm as well,
which is the other reason the second time is fast. While all this runs
the button is merely disabled, so a five-second first use reads as broken.

### What changes

Three things, independent of each other:

1. **Compression at the edge.** `encode zstd gzip` in the site block of
   every Caddyfile the repository ships. The wasm gzips to roughly a
   third; `livekit-client` (590 kB), `fonts.css` (120 kB) and the pages
   shrink too. The app itself stays uncompressed: production always has
   Caddy in front for TLS, and a let-go gzip pass for one file is not
   worth the code. Caddy's `encode` compresses only responses whose
   `Content-Type` matches its default list. Checked 2026-10-04 with the
   `caddy:2` image (v2.11.6) serving a file as `application/wasm`: the
   default list covers it (`Content-Encoding: gzip` came back), and does
   not cover `application/octet-stream`, so the model (250 kB) stays raw,
   which is fine. Measured on the vendored files: the wasm is 9,423,986
   bytes raw, 2,869,756 gzipped (level 6), 2,720,469 with zstd;
   `livekit-client` goes from 594 kB to 151 kB. uncloud bundles its own
   Caddy; the staging deploy is checked with `curl` after the merge
   (task 2) and the explicit `match` form below is the fallback if that
   Caddy is older.

2. **A loading state on the blur buttons.** While a switch to *on* is in
   flight (`blurBusy` set and the target is on), both blur buttons get
   `data-busy`, `aria-busy="true"`, and the label `Loading blur…`. CSS
   draws a thin spinning ring over the button's edge and dims the icon;
   `prefers-reduced-motion` turns the spin into a still ring. Switching
   off is instant and gets nothing. The lobby notice and the call's
   status line are not touched: the button is where the person is
   looking.

3. **Prefetch from the lobby, on a desktop.** When the lobby's tracks are
   acquired and blur is not remembered (a remembered blur loads the
   assets itself), a desktop page fetches the three assets with low
   priority so they sit in the HTTP cache before the button is pressed;
   MediaPipe's own fetch of the same immutable URLs is then a cache hit.
   Once per page load. A handheld (the page's `handheld` test) never
   prefetches: 9 MB to a phone that may never blur is the cost the blur
   plan refused. Nor does a browser that says `navigator.connection.saveData`.
   The prefetch is fire-and-forget: its failure means nothing, the click
   path handles its own failures as today.

### Why not ship a smaller wasm or compress in the app

Only the SIMD wasm is vendored already; the model is 250 kB. There is
nothing to trim. App-level compression would help only a deployment
without a proxy, which production never is.

### Testing

- Caddy: a local `caddy:2` container in front of the built binary, asked
  for the wasm with `Accept-Encoding: gzip`, answers with
  `Content-Encoding` (task 1). `scripts/docker-compose-smoke.sh` gains the
  same check so CI holds it.
- e2e, `e2e/tests/blur.spec.js`: the delayed-wasm test already in the
  file also asserts `data-busy` on the lobby button while the wasm is
  held and its absence after; a new test asserts a desktop lobby requests
  the wasm without a click, and a phone-UA lobby does not.

### Task 4: Prefetch the blur assets from a desktop lobby

**Files:**
- Modify: `resources/public/room.html`
- Test: `e2e/tests/blur.spec.js`

- [x] **Step 1: Write the e2e test**
  New test "a desktop lobby prefetches the wasm, a phone does not":
  Both halves collect requests from before the page navigates: an
  `init` function passed to `openLobby` does
  `context.on('request', r => { if (/vision_wasm_internal\.wasm$/.test(r.url())) wasmRequests.push(r); })`
  on the context before the page opens (the hook exists for exactly
  this, see `helpers.js`).
  - A desktop lobby (default context options) with blur not remembered:
    `expect.poll(() => wasmRequests.length, { timeout: 15_000 }).toBe(1)`
    without any click on a blur button. Then click `#blur-preview`; blur
    turns on (`window.call.blur` true) and the count is still 1: Chromium
    serves MediaPipe's fetch from the cache because the response is
    `immutable`. (If a second request is seen because the in-flight
    prefetch is not shared, drop the count-after-click assertion and
    note it in the summary; the prefetch still warms the cache.)
  - A handheld lobby: the same `init`, plus `userAgent` set to a Pixel
    UA string (any string containing `Android`) and
    `isMobile: true, hasTouch: true`; after the preview has frames
    (`videoWidth > 0`) wait 3 s and expect `wasmRequests.length` 0.
  Run: `lgx build && cd e2e && npx playwright test blur --workers 1`
  Expected: FAIL (no prefetch yet).
  > Deviation: the desktop half runs in a persistent context
  > (`chromium.launchPersistentContext`) and asserts on the resource
  > timing `transferSize`s, not on request events. Checked 2026-10-04:
  > Playwright's usual contexts behave like private windows, whose
  > in-memory cache never stores an entry the size of the wasm, so every
  > fetch there downloads it. A profile with a disk cache serves the
  > second fetch with a transfer size of 0. Request events fire for cache
  > hits too, so they cannot tell the two apart.

- [x] **Step 2: Implement `prefetchBlur`**
  In the blur section: a `let prefetched = false;` and
  `function prefetchBlur()` that returns at once when `prefetched`,
  `handheld`, `!blurSupported()`, or `navigator.connection && navigator.connection.saveData`;
  otherwise sets `prefetched`, builds `base` as `switchBlur` does, and
  for the three names (`vision_wasm_internal.js`, `vision_wasm_internal.wasm`,
  `selfie_segmenter.tflite`) calls `fetch(url, { priority: 'low' }).catch(() => {})`
  without awaiting. Factor the base URL into a small `blurBase()` used by
  both `switchBlur` and `prefetchBlur`. Call it from `restoreBlur` in the
  `else` branch of `if (remembered())`, so a remembered blur (which loads
  the assets itself) never races a prefetch, and a lobby that starts over
  does not fetch again.

- [x] **Step 3: Run the blur tests, then the whole e2e suite**
  Run: `lgx build && cd e2e && npx playwright test blur --workers 1`
  Expected: PASS.
  Run: `lgx e2e`
  Expected: PASS (a blur file failure under parallel load is re-run with
  one worker before it counts; see the lobby plan's summary).
  > Blur file alone: 7 passed. Full suite: 73 passed, 1 failed: the
  > known timeout of "blurred into the call…" under parallel load, a test
  > this change does not touch. That test passed twice on one worker.
