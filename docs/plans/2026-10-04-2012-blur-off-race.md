# Blur Switched Off Too Soon Freezes the Page: Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Switching background blur off right after switching it on never freezes the page.

**Tech Stack:** `@livekit/track-processors` 0.8.1, patched by `scripts/vendor-blur.patch` and bundled by `scripts/vendor-blur.mjs` (`lgx vendor-blur`) into `resources/public/track-processors.js`; Playwright e2e (`lgx e2e`).

---

## Design

### The bug

Found 2026-10-04 while verifying staging. Blur on, then off, then Join,
all within about a second, froze the page's main thread completely:
`page.evaluate` got no answer. It reproduced locally on master and on
b79e6b7 (before that day's work), in one to two runs of four. With a few
seconds between the steps it never happened.

Pausing the frozen page through the DevTools protocol (`Debugger.pause`)
showed where it was: the blur transformer's `transform`, inside
MediaPipe's `segmentForVideo` (`addProtoToStream`, then wasm), for a
frame that arrived after blur had been switched off.

The race is in `src/transformers/BackgroundTransformer.ts` of
`@livekit/track-processors` 0.8.1, the newest release:

1. `transform` checks `this.isDisabled` once, at its start.
2. On the first frame it then awaits `requestVideoFrameCallback` on the
   input video (to let a copy of that frame paint first).
3. Switching blur off calls `destroy`: `isDisabled = true`, then
   `await this.imageSegmenter?.close()`.
4. The awaiting `transform` resumes, past its only check, and calls
   `this.imageSegmenter?.segmentForVideo(...)` on the closed segmenter.
   The wasm never returns, and the page is frozen for good.

Join is not needed: the freeze comes as soon as the delayed callback
fires. Join only happened to be the next thing the probe did. The
window is the first frame's wait, which is why blur switched off a few
seconds after it went on is safe.

Checked 2026-10-04: delaying every `requestVideoFrameCallback` by 2 s
(an init script in the page) widens the window enough that blur on, then
off at once, freezes the page in three runs of three. That makes the
bug testable without retries.

### The fix

A second section in `scripts/vendor-blur.patch`, for
`src/transformers/BackgroundTransformer.ts`:

- **In `transform`, after the first-frame wait:** check again. If the
  transformer was destroyed meanwhile (`this.isDisabled`) or has no
  segmenter, return without segmenting. The copy of the frame is already
  enqueued, and the `finally` closes the original, as it does today.
- **In the segmentation promise:** with no segmenter, resolve at once.
  Today `this.imageSegmenter?.segmentForVideo(...)` on an undefined
  segmenter skips the call and never resolves, and `await
  segmentationPromise` would then hang the transform, though not the
  page.
- **In `destroy`:** take the segmenter off the transformer before closing
  it (`const segmenter = this.imageSegmenter; this.imageSegmenter =
  undefined; await segmenter?.close();`). A transform that is between
  its checks and the call then finds no segmenter instead of a closed
  one.

`init` creates a new segmenter, so a transformer restarted with the
track (camera off and on, a device switch) is unaffected. The page
creates a new processor for each switch to on, so nothing else reuses a
destroyed one.

The patch's header gains a paragraph saying what this section fixes and
why. The rebuilt bundle changes `track-processors.js`. Its `/static/v/`
version (`routes.lg`, a hash of the cached files) moves with it, so
browsers fetch it again. The wasm and the model do not change, so the
`/static/blur/<tag>/` tag stays.

### Not done

- Reporting the race upstream. Worth doing, but outside this repo. The
  summary links the source lines so an issue is easy to file.
- The page's own blur logic (`room.html`) is not changed: it already
  serialises switches (`blurBusy`), and the race is inside the library.

### Testing

A new e2e test in `e2e/tests/blur.spec.js`: an init script delays
`HTMLVideoElement.prototype.requestVideoFrameCallback` by 2 s. In the
lobby, blur on, wait until `window.call.blur` is true, switch it off at
once, wait 4 s, then ask the page something with a 10 s limit (a
`Promise.race` around `page.evaluate`, because a frozen page never
answers and Playwright's own timeout is not reached first). Expect an
answer, blur off, and a working Join afterwards. Without the fix it must
fail; this is the step that proves the test.

The existing test "blurred into the call, through camera off and on, and
off again" times out now and then under parallel load. If this race was
the cause, it stops. Task 3 runs it repeatedly to see; if it still
flakes, that is recorded, not chased here.

### Task 1: The failing test

**Files:**
- Modify: `e2e/tests/blur.spec.js`

- [x] **Step 1: Write the test**
  "blur switched off while its first frame waits does not freeze the
  page", as in the design. Pass the init script through `openLobby`'s
  `init` option (`context.addInitScript`). Use the file's existing
  helpers (`blurOf`, `POLL`) and force or evaluate clicks while blur
  runs, as the file's header explains. The init script also sets a
  flag on `window` when the delayed callback is registered (the first
  frame has started its wait), and the test polls that flag before it
  switches blur off, so the switch lands in the window on a loaded
  machine too, not only by timing. The freeze check:
  ```js
  const answer = await Promise.race([
    alice.evaluate(() => 'answers'),
    new Promise(resolve => setTimeout(() => resolve('frozen'), 10_000)),
  ]);
  expect(answer).toBe('answers');
  ```
  Then `window.call.blur` is false, and Join works
  (`window.call.joined` becomes true).
