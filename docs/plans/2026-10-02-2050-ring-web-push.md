# Ring the Other Person (Web Push) Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A signed-in person waiting alone in a room presses "Ring Anna", and Anna's subscribed devices show a notification, "<name> wants to talk", that opens the room.

**Status: completed** (2026-10-02, branch `ring-web-push`); Task 9, the device checks, waits for the staging deploy.

**Tech Stack:** let-go 1.13.0 (`src/quickmeet/*.lg`), a small Go shim over `github.com/SherClockHolmes/webpush-go` v1.4.0 linked in as a `:go/local` coord, sqlite + ragtime migrations, ruuter, a push-only service worker and plain JavaScript pages in `resources/public/`, `lgx test`, Playwright (`lgx e2e`).

---

## Design

### What it is, and what it is not

Rooms stay the model: no contacts table. A ring notifies **the other
signed-in members of the room** (`room_members` minus the caller) on every
device they have subscribed. The minimal version, agreed in discussion:

- The Ring button lives on the call page only, while the caller waits alone.
- One push per press per subscribed device. Nothing repeats by itself.
- No ring state: no decline, cancel, timeout or "missed" record. The
  notification says "<name> wants to talk", so an unanswered one left in
  the notification centre is the missed-call trace.
- Answering is tapping the notification: it opens `/room/<id>`, the
  existing lobby shows who is waiting, and Join is the answer. The lobby
  stays because iOS needs a tap inside the page before remote audio plays.
- Permission is never asked automatically: a banner on the list page and a
  switch in Settings, each a deliberate tap.

Out of scope, each goes to the backlog (Task 8): a call shortcut on the
list row; ring state (decline, cancel, missed in history); rings from
guests.

Callees are mostly iPhones (push works only in the app installed to the
home screen, iOS 16.4+) and some desktops.

### Verified before planning

- `webpush-go` v1.4.0 cannot be a `:go/interop` coord: its only entry
  point is `SendNotification(message []byte, s *Subscription, options
  *Options)`, two structs, and lgx generates no struct constructors
  (KNOWLEDGE.md, "Two wrapper shapes"). It needs a hand-written shim, the
  shape `letgo-packages/livekit/shim/shim.go` has. It exports
  `GenerateVAPIDKeys() (privateKey, publicKey string, err error)`.
- A VAPID public key and a subscription's `p256dh` are the same thing: an
  uncompressed P-256 point, base64url. So a generated VAPID public key is
  a valid `p256dh` for tests.
- There is no service worker today; the manifest is `display: standalone`
  with scope `/`, which is what iOS push needs.

Not verifiable before deploying (needs HTTPS and a real iPhone), so they
are Task 9: whether a notification tap opens the installed app at the room
URL, whether a same-tag ring replaces the earlier notification, and
whether Apple accepts the VAPID subject.

### The shim (`webpush/`, namespace `webpush.shim`)

A Go module inside this repository, linked through a `:go/local` coord, in
the style of the livekit shim (registered in `init()` with
`vm.NewNamespace` / `ns.Def` / `rt.RegisterNS`, no generated bindings).
In-repo rather than a new letgo-packages release: it is about sixty lines
with one consumer, and one PR ships it. It can move to letgo-packages
unchanged if a second app wants it.

Two functions, both in the `(value, error)` shape the livekit shim proves
crosses the boundary:

```go
// "<private> <public>", both base64url, joined by one space.
func GenerateVAPIDKeys() (string, error)

// The push service's HTTP status. An error only when nothing was sent
// (bad key, encryption failure, no connection, timeout).
func Send(endpoint, p256dh, auth, payload, subject, publicKey, privateKey, topic string, ttl int) (int, error)
```

`Send` builds the `Subscription` and `Options` (`TTL`, `Topic`,
`Urgency: high`, `Subscriber`, the VAPID pair, an `http.Client` with a
10-second timeout), calls `SendNotification`, closes the response body and
returns the status code. The shim knows nothing about allowlists or the
database.

### Storage (migration `004-push`)

```
settings            key text primary key, value text not null
push_subscriptions  endpoint   text primary key,
                    session_id text not null references sessions(id),
                    p256dh     text not null,
                    auth       text not null,
                    created_at text not null default CURRENT_TIMESTAMP
```

- **VAPID keys** are generated on first start and kept in `settings` under
  the key `vapid-keys`, as the shim's one string (one row, so the pair
  cannot be half-written). No new environment variable. Losing the
  database loses the keys, and with them every subscription, which the
  same loss would take anyway.
- **A subscription belongs to a session**, so it stops when the session
  does: `db/delete-session!` deletes the session's subscriptions first.
  A subscription whose session expired (the 365-day window of
  `session-user-sql`) or whose address left the allowlist is never rung:
  the target query joins live sessions, and the route filters with
  `auth/allowed?`.
- Saving is an upsert on `endpoint`: the same browser subscribing again,
  under another session or with rotated keys, replaces the row.

### `quickmeet.push`

A small namespace between the routes and the shim:

- `(push/keys! conn)` → `{:public "..." :private "..."}`, generating and
  storing them when `settings` has none (insert-or-ignore, then read
  back).
- `(push/endpoint-problem endpoint)` → nil or a message. The server posts
  to whatever endpoint a signed-in person hands it, so the endpoint must
  be `https://` and its host one of the browser vendors' push services:
  `fcm.googleapis.com`, or a host ending in
  `.push.services.mozilla.com`, `.push.apple.com` or
  `.notify.windows.com`. At most 2048 characters. Anything else is
  refused: without the list any account could make the server send
  requests into the box's own network.
- `(push/deliver! push conn targets message)` sends one message to each
  target through `(:send! push)`, off the request thread through
  `(:spawn push)`, and deletes a subscription whose push service answers
  404 or 410 (gone for good). Any other outcome, an exception included,
  is one `println` line (`quickmeet: push to <host> failed: ...`) and
  nothing else. `message` is `{:payload json-string :topic room-id
  :subject "..."}`.

The handler receives a fifth argument, `push`:

```clojure
{:public-key "..."                           ; what the pages subscribe with
 :send!  (fn [target message]) -> status     ; the shim's Send in production
 :spawn  (fn [f])}                           ; (future (f)) in production
```

`routes.lg`'s `ig/init-key` builds it from `push/keys!` and the shim.
Tests pass a recording `:send!` and a `:spawn` that calls `f` at once, so
nothing in a route test is asynchronous and nothing leaves the machine.
The TTL (3600 s) is a constant in `push.lg`.

### The API

```
GET  /api/push/key            -> 200 {"key": "<VAPID public key>"}
POST /api/push/subscriptions  {"endpoint", "keys": {"p256dh", "auth"}}
                              -> 200 {} | 400 | 401 | 415
POST /api/push/unsubscribe    {"endpoint"} -> 200 {} | 401 | 415
POST /api/rooms/:id/ring      -> 200 {"devices": n} | 401 | 403 | 404 | 409 | 429
POST /api/rooms/:id/token     gains "ring": ["Anna", ...]
```

- **Subscribe** takes the body `PushSubscription.toJSON()` produces. 400
  for a refused endpoint or for `p256dh`/`auth` that are blank or longer
  than 256 characters. The row is tied to the request's session id.
- **Unsubscribe** deletes the row only if it belongs to one of the
  caller's own sessions; an unknown endpoint is still 200.
- **Token** adds `ring`: the distinct display names of the people a ring
  from this caller would reach, `[]` for a guest or when nobody can be
  reached. The call page shows the button from it.
- **Ring**, checked in this order:
  1. no session → 401;
  2. no such room → 404;
  3. the caller is not in the room right now (`user:<id>` is not among
     `(participants id)`, or the SFU could not be asked) → 403. Being in
     the room implies being a member, since the token endpoint adds one;
  4. nobody to reach → 409 `{"error": "nobody to ring"}`;
  5. the cooldown → 429 with `Retry-After`: a new rate-limit bucket,
     `:ring {:limit 1 :window-ms 30000}`, keyed by user id and room id.
     Checked last, so only a ring that would be sent starts the window.
     Like every limit it is off under `RATE_LIMIT=false`;
  6. otherwise deliver and answer 200 with how many devices were tried.

**Targets** (`db/ring-targets conn room-id caller-id`): subscriptions
joined to live sessions, their users, and `room_members` of this room,
excluding the caller's own user id; then filtered by `auth/allowed?`.
A room that gathered three signed-in members rings both others; the cap
of two per room bounds the call, not the membership.

**The message**:

```json
{"title": "Anna wants to talk", "body": "Tap to join the call.",
 "url": "/room/0123456789ab", "tag": "room-0123456789ab"}
```

`title` uses the caller's display name. `Topic` is the room id (12 hex
characters, valid for the header), so a ring still waiting at the push
service is replaced by the next one for the same room. The VAPID subject
is `https://<host>` when the request came over TLS
(`x-forwarded-proto`), else `quickmeet@localhost` (the library prefixes
`mailto:`; check `vapid.go` for the exact rule).

### The service worker (`resources/public/sw.js`, served at `/sw.js`)

Push only. No `fetch` handler and no caching, so it can never serve a
stale page.

- `push`: parse the JSON and `showNotification(title, {body, tag,
  renotify: true, icon: '/static/icon-192.png', data: {url}})`, inside
  `event.waitUntil`. A push without readable JSON still shows a generic
  "quickmeet" notification: iOS revokes a subscription whose pushes show
  nothing.
- `notificationclick`: close the notification; if a window of the app is
  already at `data.url`, focus it; otherwise `clients.openWindow(url)`.

It is served from a route of its own, `/sw.js`, because a worker's scope
is limited by where its file lives and `/static/sw.js` could only control
`/static/`. `Cache-Control: no-cache`, so a changed worker is picked up.
The worker is registered only when someone turns notifications on; people
who never do get no service worker.

### The pages

**Shared helpers in `ui.js`** (a `push` object):

- `push.supported()`: `serviceWorker`, `PushManager` and `Notification`
  all exist.
- `push.needsInstall()`: an iPhone or iPad (`/iPhone|iPad/` in the user
  agent, or a `Mac` user agent with `navigator.maxTouchPoints > 1`) that
  is not running standalone (`navigator.standalone !== true`) and has no
  push support.
- `push.subscription()`: the browser's current subscription or null
  (through `navigator.serviceWorker.getRegistration('/')`; never
  registers).
- `push.on(email)`: **first** `Notification.requestPermission()`, before any
  other `await`, because Safari only shows the prompt while the tap is
  still the active gesture. Then register `/sw.js`, wait for
  `navigator.serviceWorker.ready`, fetch `/api/push/key`, subscribe with
  `{userVisibleOnly: true, applicationServerKey: <the key as a
  Uint8Array>}` (decode base64url by hand; not every Safari takes the
  string), and POST the subscription. Throws a sentence when permission
  is refused or subscribing fails.
- `push.off()`: unsubscribe in the browser and POST
  `/api/push/unsubscribe`.
- `push.sync(email)`: called with the signed-in person's address. If the
  browser has a subscription, it is posted again (an upsert, so it heals
  a row lost to a rotated subscription or a new session), but only when
  both of these hold; otherwise the browser's subscription is dropped
  (`unsubscribe()`, no server call) and the banner offers it afresh:
  - `localStorage['quickmeet.push.user']` equals `email`: the person who
    turned it on is the one signed in;
  - the subscription's `options.applicationServerKey` equals the key
    `/api/push/key` serves (compare as base64url): a database that lost
    its VAPID keys cannot use an old subscription.

The browser's subscription is the state. `localStorage` holds two things
beside it: the banner's dismissal, and `quickmeet.push.user`, the address
that turned ringing on, which `push.on(email)` writes and `push.off()`
removes.

The shared sign-out handler removes `quickmeet.push.user` first (that
cannot fail), then calls `push.off()` (errors ignored), then posts
`/api/auth/signout`. So the next person to sign in on that browser is
never rung without having asked: even if unsubscribing failed, `sync`
finds no matching owner and drops the leftover subscription instead of
adopting it. The server side holds on its own too, since deleting the
session deletes its subscriptions.

**List page (`index.html`)**: a banner above the list, for a signed-in
person only.

- With `push.supported()`, no subscription, `Notification.permission` not
  `denied`, and not dismissed: "Let people ring you on this device." with
  **Turn on** and **Not now**. Turn on calls `push.on()` and hides the
  banner on success; a failure shows its sentence in the banner.
- With `push.needsInstall()` and not dismissed: "To be rung on this
  iPhone, add quickmeet to your home screen (Share, then Add to Home
  Screen) and open it from there." with **Not now** only.
- Not now stores `quickmeet.push.dismissed` in `localStorage` and hides
  it for good on that device.
- On load the page first calls `push.sync(email)` (the address from
  `/api/me`), then decides about the banner. `/api/me` already returns
  `email`.

**Settings (`settings.html`)**: a "Notifications" block under the name
form: one button, "Let people ring me on this device" / "Stop ringing
this device", by whether a subscription exists, and one line of status:
the install hint when `needsInstall()`, "Notifications are blocked for
this site in the browser's settings." when permission is `denied`, "This
browser cannot receive rings." when unsupported.

**Call page (`room.html`)**: a `#ring` button in the overlay under
`#invite`, visible only while waiting (the CSS rule `#invite` has) and
only when the token's `ring` list is not empty. Its label is "Ring
<name>" for one name and "Ring them" for more. A press posts
`/api/rooms/<id>/ring`; on 200 or 429 the button reads "Rung" and stays
disabled for 30 seconds, then returns. Any other answer shows "Could not
ring." in the status line for a few seconds, the way `blurFailed` does.
`window.call.ring` holds the names, for tests.

### Testing

  the same; `endpoint-problem` accepts each vendor host and refuses
  `http://`, other hosts, look-alikes (`fcm.googleapis.com.evil.example`)

  (base64url) as `auth`: the server sees a POST with `ttl: 3600`,
  `content-encoding: aes128gcm`, `urgency: high`, the `topic`, and an
  `authorization` starting `vapid`, and `Send` returns the status the
  server answered.
- `test/quickmeet/db_test.lg`, `migrations_test.lg`: the new tables, the
  upsert, `ring-targets` (other members only, live sessions only),
  deleting a session deletes its subscriptions.
- `test/quickmeet/routes_test.lg`: subscribe (401, 415, 400 for a bad
  endpoint, 200 and the row), unsubscribe (only one's own), the key
  endpoint, `ring` in the token response, and the ring route's six
  outcomes with a recording `:send!`, including the payload, the topic,
  that the caller's own devices are not rung, that a disallowed address
  is not rung, and the cooldown with a limiter.
- e2e (`e2e/tests/ring.spec.js`): `/sw.js` is served as JavaScript.
  Bob signs up, joins the room once through the API (which makes him a
  member) and stores a subscription through
  `page.request.post('/api/push/subscriptions')` with an allowed endpoint
  and a `p256dh` of `AAAA`, which fails in the shim's encryption before
  any network call. Alice joins the room: "Ring bob…" shows; a click
  turns it to "Rung" and disables it; when Bob joins the button is gone.
  A room with no other member shows no button. The banner: in a context
  with `notifications` granted it shows, "Not now" hides it, and it stays
  hidden after a reload. Real subscribing does not work in the headless
  shell (no push service), so `push.on()` is checked on devices; a
  mocked `PushManager` would test the mock. The account-switch rule of
  `push.sync` is tested without one: an init script replaces
  `push.subscription` with a fake whose `unsubscribe` is recorded, sets
  `quickmeet.push.user` to another address, and the test asserts that
  loading the list calls `unsubscribe` and posts nothing to
  `/api/push/subscriptions`.
- The existing suites must stay green: in the default headless context
  `Notification.permission` is `denied`, so the banner is absent there.
  If that turns out not to hold, the banner must still not cover or
  shift anything an existing spec clicks.

## Completion Summary

**Implemented.** A signed-in person waiting alone in a room presses
"Ring <name>", and every device the room's other members turned ringing
on for gets a Web Push: "<name> wants to talk", which opens the room's
lobby. The server side is a Go shim over webpush-go in `webpush/`,
`quickmeet.push` (VAPID keys made on the first start, the push-service
allowlist, delivery on futures with 404/410 cleanup), migration
`004-push`, and the ring, key and subscription endpoints with a
30-second limit. The pages have a push-only service worker at `/sw.js`,
the `push` helpers in `ui.js`, a banner on the list, a switch in
Settings, and the Ring button on the call page. Sign-out stops the
device. Docs and four backlog entries are updated.

**Verified.** `lgx test`: 81 tests, 578 assertions, 0 failures in 4 of 6
full runs (the other two hit the flake below). `lgx e2e`: 50 passed and
2 blur timeouts under parallel load; `blur.spec.js` with `--workers 1`
passed 5 of 5. `ring.spec.js` passes 7 of 7. End to end against the
built binary: a ring from the call page to a stored device on Google's
real push service (a real P-256 key, an endpoint no browser holds)
answered 200, encrypted, signed and posted over TLS, and FCM's answer
deleted the subscription, as a 404 or 410 should. Whether FCM checks the
VAPID signature before it looks up the device is not known from this;
the device checks in Task 9 settle it.

**Issues found on the way.**
- The headless shell reports `Notification.permission` as `denied`
  whatever is granted; the spec overrides the getter.
- `system_test.lg`'s `participants-of-an-unknown-room` fails now and then
  in full runs, on master too (1 of 4 there).
  `docs/backlog/system-test-sfu-unreachable-at-start.md`.
- Codex's per-task reviews found two real issues, both fixed: sign-out
  waited without limit on unsubscribing (now 3 s at most), and a failed
  ring could put an occupied call back into the waiting state.

**Deviations, in one place.**
- `the-allowlist` route test passes the handler's new `push` argument;
  `with-handler` has a five-argument form.
- The banner tests tell the page notifications were not asked yet,
  because of the headless quirk above.
- While Ring is shown, Copy link is the plain button; Ring has a new
  `bell` icon.
- `INSTALL.md`'s password-reset SQL deletes push subscriptions first; its
  Backups section names the ringing keys.
- The `/sw.js` route landed in Task 4 and its test in Task 5, with the
  file.

**What the plan could have specified better:** the browser-test strategy
for anything permission-gated. It assumed a granted permission would read
as granted in the headless shell, which it does not; checking that in a
two-line probe before writing the test plan would have saved a round.
