# M3: accounts — Implementation Plan

> **For agentic workers:** Use executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The smallest auth that gates starting a call: email and password accounts, cookie sessions in sqlite, an operator allowlist, and a display name; guests still join from a link with nothing.

**Tech Stack:** let-go 1.13.0 on lgx 0.4.2, `golang.org/x/crypto/bcrypt` as a `:go/interop` coord (the first Go coord the app declares itself), sqlite through the existing `sqlite`/`ragtime` packages, HoneySQL rendered at load time, plain DOM pages, Playwright 1.56.0. No new JS dependencies.

## Design

### Where M3 stands

M2 shipped on 2026-09-29 (commit 5c72bd5): rooms are permanent, hold two people, and the room page is a product. Staging at `https://quickmeet.absky.dev` is public: anyone who finds it can click "New meeting". The roadmap's rule (resolved 2026-09-28) is that signed-in users start calls and anyone with a link joins. M3 builds that rule; M4 (contacts, history) hangs off the accounts it creates.

### Facts this design rests on (verified 2026-09-29)

- `golang.org/x/crypto/bcrypt` works as a `:go/interop` coord with no shim. Probed in a scratch project on the built runtime: `(bcrypt/GenerateFromPassword "pw" 10)` takes a let-go string (it unboxes to `[]byte`) and returns the hash as a let-go string (`[]byte` boxes to a string, `pkg/vm/value.go:233`). `(bcrypt/CompareHashAndPassword hash "pw")` returns `nil` on a match and, because a lone `error` result is boxed rather than raised, a Go error *value* on a mismatch: check with `nil?`, do not `try`. `(bcrypt/Cost hash)` reads the cost back. livekit-server already pulls `golang.org/x/crypto` into the runtime, so the coord pins a version that is already in the module graph (v0.56.0 is in the cache).
- let-go's http server lowercases request header names and joins repeated values with commas (`pkg/rt/http.go:258-263`), so the cookie header is `(get-in req [:headers "cookie"])`, one string, `name=value; name=value`. Response `:headers` is any seq of `[name value]` pairs, added with `Header.Add` (`http.go:300-322`), so a map works and one `Set-Cookie` per response is enough here.
- `random-uuid` reads `crypto/rand` (`pkg/rt/lang.go:3205`): 122 random bits, enough for a session id. `(str (random-uuid))` carries the `#uuid` tag; strip to hex as `routes/new-room-id` does.
- let-go's `string` namespace has `lower-case`, `trim`, `split`, `includes?`, `join`, `replace`; `(now)` is a `go.time.Time`. Session expiry is compared in SQL instead (`datetime('now', '-30 days')`), which keeps time handling out of let-go.
- Handlers share one dynamic-binding stack (backlog `letgo-http-handlers-share-dynamic-bindings.md`): every new query is rendered at load time in `db.lg`, parameters only at request time.
- `deploy.yml` passes `APP_DOMAIN` from a repository variable into `uc deploy` as an environment variable and `compose.yaml` interpolates `${APP_DOMAIN}`; `ALLOWED_EMAILS` can travel the same way.
- CI keys the runtime cache on `lgx.edn` (`test.yml`), so the new coord rebuilds the runtime once on the first CI run and is cached after.

### Key decisions

1. **Passwords, not magic links.** A magic link needs SMTP, which is a second service to configure and a dependency the "one binary, minimal installation" rule was written to avoid. Passwords need only the bcrypt coord, which the roadmap named as the first thing to try, and the probe shows it costs one line. The allowlist race the roadmap flagged is accepted and documented: with no proof of address, whoever registers an allowed address first owns it. On a personal instance the operator adds an address and tells the person to sign up; if that ever bites, verification email is an M6-style addition that does not change the data model. No password reset in v1 for the same reason (no email); the operator can delete the row.
2. **Sessions are opaque ids in sqlite.** A `sessions` row (`id`, `user_id`, `created_at`); the cookie is `session=<32 hex chars>`, `Path=/; HttpOnly; SameSite=Lax; Max-Age=2592000`, plus `Secure` when the request came through TLS (`x-forwarded-proto` is `https`), since development is plain http on localhost. A session older than 30 days is not a session; the lookup query says so. Sign-out deletes the row and clears the cookie. Nothing is signed: let-go has no HMAC, and a random id in the database needs none.
3. **The allowlist is one function asked at three points.** `ALLOWED_EMAILS` is parsed once at system start into a set of normalised addresses, or `nil` when unset. `allowed?` gates sign-up, sign-in, and `current-user` on every request, so removing an address ends that account's access at its next request. Unset means open sign-up (the README says so, and staging stays that way until the operator sets the variable).
4. **Three namespaces, thin routes.** `quickmeet.password` (hash, check; the only place that names bcrypt), `quickmeet.auth` (normalise and validate an email and a password, `allowed?`, `sign-up!`, `sign-in!`, `current-user`, `sign-out!`, cookie parsing and the `Set-Cookie` value), `quickmeet.db` (the queries, rendered at load time). `routes.lg` maps requests to those and answers JSON. The handler takes a fourth argument, `auth`, `{:allowed-emails #{..} | nil}`; tests pass it directly, the integrant component builds it from the config.
5. **Gating is minimal.** `POST /api/rooms` needs a session and records `rooms.owner_id`. `GET /api/rooms/:id`, the token endpoint and the room page stay open: joining a link never requires an account. The join token is unchanged (a guest and a signed-in person mint the same kind); the room page pre-fills the name field with the display name, which is what M4's "join tokens carry account identity" will later replace with the account id.
6. **Pages follow the existing pattern.** Static HTML in `resources/public/` with a little DOM code and `fetch`, no framework: `/signup`, `/signin`, `/settings`. The landing page asks `GET /api/me` on load and shows either "Sign in" and "Sign up" links or the "New meeting" button with the display name, a settings link and a sign-out button. Errors are shown from the JSON `error` field.
7. **Validation is small and server-side.** Email: trimmed, lower-cased, matching `^[^@\s]+@[^@\s]+$` (something before and after one `@`, no whitespace), at most 254 characters; the normalised form is the unique key. Password: 8 to 72 bytes (bcrypt reads at most 72). Display name: trimmed, 1 to 64 characters, defaults to the part of the email before `@` cut to 64 characters (the email rule guarantees it is not empty). Sign-in answers the same `invalid email or password` for an unknown address and a wrong password; the timing difference (no bcrypt run for an unknown address) is a user-enumeration channel accepted for v1 and listed under M6.
8. **Rooms get an owner now.** One nullable `owner_id` column on `rooms`, set on creation. Nothing reads it in M3, but M4 needs it and rooms created between now and then could not be back-filled.
9. **Out of scope:** rate limits (M6), email verification and password reset (need email), contacts and history (M4), an admin page for the allowlist (it is an environment variable), account deletion.

### Schema

Migration `002-create-users`, appended in `migrations.lg`:

```
users     id TEXT PRIMARY KEY, email TEXT NOT NULL UNIQUE, password_hash TEXT NOT NULL,
          display_name TEXT NOT NULL, created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
sessions  id TEXT PRIMARY KEY, user_id TEXT NOT NULL REFERENCES users(id),
          created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP
rooms     + owner_id TEXT NULL (REFERENCES users(id))
```

Down: drop `sessions`, drop `users`, drop the column (`ALTER TABLE rooms DROP COLUMN`, supported by the bundled sqlite). Ids are 32 hex chars from `random-uuid`, made by `id/random-hex` in a new `quickmeet.id` namespace. `(str (random-uuid))` is `#uuid "..."`, and the existing `routes/new-room-id` strips non-hex characters from that, which keeps the `d` of `uuid`: every room id so far starts with `d`. `random-hex` takes the 36-character uuid out of the string first; `new-room-id` moves onto it (ids stay 12 hex chars, existing links unaffected).

### API

```
POST /api/auth/signup   {"email", "password"}
                        -> 201 {"email", "display_name"} + Set-Cookie
                         | 400 {"error": "<what is wrong>"} | 403 {"error": "not allowed"} | 409 {"error": "exists"}
POST /api/auth/signin   {"email", "password"}
                        -> 200 {"email", "display_name"} + Set-Cookie
                         | 401 {"error": "invalid email or password"} | 403 {"error": "not allowed"}
POST /api/auth/signout  -> 200 {} + Set-Cookie clearing the session
GET  /api/me            -> 200 {"email", "display_name"} | 401 {"error": "unauthorized"}
POST /api/me            {"display_name"} -> 200 {"email", "display_name"} | 400 | 401
POST /api/rooms         -> 201 {"id"} | 401 {"error": "unauthorized"}
GET  /signup, /signin, /settings   the pages
```

`current-user` is resolved per request from the cookie: a session row younger than 30 days whose user's email is still allowed. Anything else is signed out.

### Pages

- **Landing (`index.html`).** On load, `GET /api/me`. 401: show `#signed-out` (links to `/signin` and `/signup`, "New meeting" hidden). 200: show `#signed-in` ("Signed in as <display_name>", the `#new` button, a `/settings` link, a `#signout` button that posts and reloads). Element ids: `#signed-out`, `#signed-in`, `#who`, `#new`, `#signout`, `#error`.
- **Sign up / sign in (`signup.html`, `signin.html`).** A form with `#email`, `#password`, a submit button; on success `location.href = '/'`; on error `#error` shows the message. Each links to the other. On sign-up a 409 says "an account with this email already exists, sign in"; a 403 says the address is not allowed on this instance.
- **Settings (`settings.html`).** Loads `/api/me` (401 sends to `/signin`), shows the email, a `#display-name` input and a save button; on success shows "Saved".
- **Room page.** After `loadRoom`, `GET /api/me`; if 200 and `#identity` is empty, pre-fill it with the display name. Nothing else changes; guests see the same lobby.
